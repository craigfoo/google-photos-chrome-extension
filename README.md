# Upload to Google Photos (Chrome extension)

Right-click any image in Chrome → **Upload to Google Photos**. The image is
fetched, pushed to your Google Photos library through the Photos Library API,
and you get an in-page toast with a thumbnail, a progress bar, and a green
"Uploaded to Google Photos" (or a red failure with the real reason and a Retry
button). The toolbar icon badge mirrors the state.

Manifest V3, plain JavaScript, no dependencies, no build step.
**See [SETUP.md](SETUP.md) for the steps only you can do** (keys, Cloud
project, OAuth client, loading the extension), and **[STORE.md](STORE.md)** for
publishing it on the Chrome Web Store.

## Layout

| Path | What it is |
| --- | --- |
| `manifest.json` | MV3 manifest. Two placeholders you must fill in: `key` and `oauth2.client_id`. |
| `src/background.js` | Service worker: context menu, fetch, auth + token refresh, upload handshake, album lookup, toast/notification/badge feedback. |
| `src/toast.js` | The in-page toast. Injected on demand with `chrome.scripting.executeScript`; renders inside a closed shadow root. |
| `src/strings.js` | Every user-facing string (menu title, toast labels, notification text, options labels, all error messages). |
| `src/options.html/.css/.js` | Options page: "Add uploads to an album" + album name, autosaved to `chrome.storage.sync`. |
| `icons/` | 16/32/48/128 PNGs, generated by `scripts/make-icons.py`. Four Google-palette quadrants under a white upload arrow; deliberately not the Google Photos pinwheel, which the store would reject as a Google logo. |
| `scripts/derive-extension-id.js` | Prints the manifest `key` and the extension ID for a PEM private key. |
| `scripts/make-icons.py` | Regenerates the icons (pure Python, no Pillow). |
| `scripts/package.js` | Builds the Chrome Web Store zip in `dist/` with `key` stripped (pure Node). |
| `scripts/make-store-assets.mjs` | Regenerates `store/` (screenshots + promo tiles). Needs `playwright-core` and a Chrome binary; the outputs are committed so you only run it after a visual change. |
| `store/` | Store listing assets: four 1280×800 screenshots, 440×280 and 1400×560 promo tiles. |
| `docs/` | Homepage + privacy policy, served by GitHub Pages at https://photos.craigrettew.com/ (`docs/CNAME`); required by Google's OAuth verification. |

## How an upload works

1. `contextMenus.onClicked` fires with `info.srcUrl` and the tab.
2. `src/toast.js` is injected into that tab (idempotent) and told to show the
   "uploading" card. If injection is impossible the whole upload reports
   through `chrome.notifications` instead.
3. The service worker `fetch`es the image (no CORS, thanks to the `<all_urls>`
   host permission). If that still fails, or returns 401/403, it asks the page
   to fetch it instead (an injected function that runs with the page's origin
   and cookies) and ships the bytes back as base64.
4. `POST /v1/uploads` with the raw bytes → upload token (plain text).
5. If the album option is on, the album ID is resolved (cache → `albums.list`
   with pagination → `albums.create`).
6. `POST /v1/mediaItems:batchCreate` with the token (and `albumId`).
7. Toast turns green (auto-dismiss after 4 s) or red (stays until dismissed,
   Retry re-runs the same request). Badge shows `…` / `✓` / `!`.

Token refresh: every API call goes through `withAuthRetry()`. On a 401 the
cached token is dropped with `chrome.identity.removeCachedAuthToken`, a fresh
one is requested (silently first, then interactively) and the call is retried
once. A second 401 is reported as an expired/revoked sign-in.

## Assumptions and judgment calls

These were ambiguous in the brief; here is what was chosen and why.

- **Image hosts are covered by `optional_host_permissions: ["<all_urls>"]`,
  requested per origin at click time.** The brief asked for
  `photoslibrary.googleapis.com` only, and the first build shipped that way.
  In practice most images live on a CDN that does not send
  `Access-Control-Allow-Origin`, so without a host permission the service
  worker's fetch was blocked by CORS, and the in-page fallback (which uses the
  page's origin) was blocked too; the very first real upload hit this. A
  blanket `<all_urls>` host permission fixes it but shows "Read and change all
  your data on all websites" at install and draws extra Web Store review.
  So instead `chrome.permissions.request({ origins: [imageOrigin] })` is
  called synchronously in the click handler (it needs the click's user
  gesture; an `await` before it would lose that). Chrome prompts once per
  host and remembers the answer; after that the worker's fetch to that host
  is not subject to CORS. On Retry there is no gesture, so only
  `permissions.contains` is checked. If the user declines, the in-page
  fallback (`activeTab` + `chrome.scripting.executeScript`) still runs and
  works whenever the page itself may read the image.
- **A second menu item for sites that overlay their photos.** Instagram,
  Threads and Facebook put a transparent element over every `<img>` to defeat
  right-click saving, so Chrome opens the plain page menu and an
  `contexts: ['image']` item can never appear. On those sites (matched by
  `documentUrlPatterns`) a page-menu item "Upload image under cursor to
  Google Photos" is shown instead. It injects `pageFindImageUnderCursor`,
  which uses the `:hover` chain Chrome keeps alive while the menu is open,
  looks through the overlay with `elementsFromPoint`, falls back to the
  largest visible image inside the hovered ancestors (for a click on the
  caption), and returns the largest `srcset` candidate. Because their CDN
  hosts are known (`cdninstagram.com`, `fbcdn.net`), the host-permission
  prompt is still issued synchronously on the click. To cover another site,
  add its page and CDN patterns to `OVERLAY_SITES` in `background.js`.
- **`data:` and `blob:` URLs are reported, not uploaded.** The brief lists
  them under error handling, so they get their own message. (`data:` URLs
  could technically be decoded and uploaded; that is a one-function change in
  `fetchImage` if you ever want it.)
- **Mime resolution.** `Content-Type` header if it starts with `image/`;
  otherwise, if the header is missing or a generic `application/octet-stream`,
  the URL extension; otherwise `image/jpeg`. A header that is clearly
  something else (`text/html`, `application/json`, `video/*`…) is a
  "not an image" error rather than a jpeg fallback, because uploading it would
  just fail later with a worse message.
- **Thumbnail.** The toast's `<img>` simply points at `info.srcUrl`, which the
  page has already loaded, so it comes from cache and never needs a second
  fetch. If it cannot render (e.g. hot-link protection), the thumbnail is
  hidden and the card reflows.
- **Success link.** Opens the created item's `productUrl` when Google returns
  one, otherwise `https://photos.google.com`. Both land in Google Photos; the
  item link is just more useful.
- **Album lookup under the `appendonly` scope.** Google restricts
  `albums.list` to app-created albums, and with some scope combinations it
  returns 403. If listing is denied the extension creates the album instead.
  Either way the resulting ID is cached in `chrome.storage.local` keyed by
  album name. Since the March 2025 Photos API changes, the API can only see
  media and albums that *this app* created, so an album with the same name
  that you made by hand in Google Photos will not be matched; a new one will
  be created alongside it.
- **Album resolution happens after the bytes upload**, so a bad album name
  does not waste the transfer, and the same token is reused.
- **Badge** shows `…` while uploading, `✓` (green) or `!` (red) afterwards,
  and clears after 4 seconds.
- **Retry re-fetches the image**, it does not reuse the previous bytes, because
  the most likely failures (network, expired token) are fixed by a fresh
  attempt and holding large buffers in a service worker is wasteful.
- **Size limit** is checked twice: `Content-Length` before download, and the
  real byte count after.
- **Shadow root styling** uses constructable stylesheets
  (`adoptedStyleSheets`) so no `<style>` element is added to the page DOM, with
  a `<style>`-inside-the-shadow-root fallback. Either way nothing leaks. The
  one thing outside the root is a short inline `style` on the host element
  itself (`all: initial; position: fixed; width: 0; height: 0`), which is what
  stops page rules like `div { border: … }` from styling the mount point.
- **Both fetch paths send credentials.** Once the image origin is granted, the
  worker's request carries your cookies for that host, so images behind a
  cookie login usually work on the first attempt; the in-page fallback also
  uses `credentials: 'include'`.
- **File name** sent to Google is the URL's last path segment (sanitised) with
  an extension added from the mime type if missing.
- **Permissions used:** `contextMenus` (menu), `identity` (OAuth), `storage`
  (options + album cache), `notifications` (fallback feedback), `activeTab` +
  `scripting` (toast injection and in-page fetch); `host_permissions` for the
  Photos API only; `optional_host_permissions: <all_urls>` (image hosts,
  granted one at a time via `chrome.permissions.request`, which needs no
  manifest permission of its own — listing `"permissions"` there makes Chrome
  warn "Permission 'permissions' is unknown"). `action` is declared so the
  badge exists; it is not a permission. No
  `tabs` permission is needed: `tabs.sendMessage` and `tabs.create` work
  without it.
- **Store build strips `key`.** `scripts/package.js` writes
  `dist/upload-to-google-photos-<version>.zip` containing only `manifest.json`,
  `src/` and `icons/`, with `key` removed (the store manages its own key pair)
  and refuses to run while `client_id` is still the placeholder. Nothing in
  `dist/` is committed.

## Keep your key out of git

`.gitignore` excludes `*.pem` and `dist/`. Store the private key from SETUP
step 1 outside this folder anyway. (Once you follow STORE.md, the store's own
key replaces it and the `.pem` is no longer used.)
